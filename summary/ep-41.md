# 第 41 期 当人工智能碰到竞技体育

## 内容摘要

本期从马斯克在 Twitter 上公布所谓 2020 年美国大选“深度黑幕”的话题切入，随后回到世界杯的半自动视频助理裁判、毫米级出界判定和智能足球，讨论 AI 与体育规则、裁判权威及人机协作之间的新问题。节目接着分析 KataGo 被对抗算法稳定诱导出错的案例，并把它延伸到图像识别、自动驾驶和未来智能化社会的可靠性风险。

中段以疫情期间大规模转向线上的学术会议为例，讨论统一工具采购、预录制、Panel 讨论、付费社群和参会体验等组织问题。开源社区举办年会和评选活动的经验则说明，技术能力之外，产品设计、互联网运营、奖项命名、用户路径和分散风险同样决定一个活动能否形成口碑。

后半段承接上一期软件工程讨论，从“Rust 成为巨坑”的案例谈技术决策不能被热门程度或个人简历驱动，技术是否适合团队、产品阶段和可靠性要求才是关键。节目最后提出“开放式软件工程”的视角：现代软件大量依赖第三方开源组件，学校应把选型、组合、依赖生命周期、安全和合理复用纳入工程教育，并根据课程真正想培养的能力设计考核。

## 时间线

### 00:00-13:24：世界杯 VAR 与裁判权威

- 开场简要讨论马斯克在 Twitter 上公开的一系列关于 2020 年美国大选的材料；节目认为其政治影响仍需继续观察，不能仅凭第一轮传播就下结论。
- 世界杯的半自动视频助理裁判通过高速摄像、多个机位和实时分析，帮助判断越位、出界和进球等现场难以确认的情况。
- 日本对西班牙比赛中的出界争议被用作例子：国际足联后来解释称，足球在地面上的投影仍有 1.8 毫米压在线上，因此进球判定有效。
- 智能足球已经可以采集球速、传球等数据；未来如果球员也携带定位设备，越位和跑位可能由系统即时判断，但这会进一步改变主裁判的最终权威和足球的规则结构。
- VAR 不是简单地让裁判“更准确”：当机器结论与裁判直觉不一致时，规则需要重新回答谁拥有最终决定权，以及比赛连续性应如何保留。

### 13:24-25:39：KataGo 漏洞与对抗 AI

- 研究团队用专门的对抗算法攻击围棋 AI，在让系统胜率判断极高、棋盘上形成特定环形棋块等条件下，诱导 KataGo 走出人类棋手容易看出的必败着法。
- 这个错误具有较高的可复现性：AI 在特定节点会把胜率极高的局面判断错，人工替它走一步后，系统又可能恢复正常判断。
- 节目把围棋案例与图像识别中的不可见噪声、自动驾驶中误导识别的图案联系起来，指出不同 AI 系统可能共享“在特殊模式下被稳定欺骗”的脆弱性。
- “99% 的准确率”不能简单代表可靠。人类通常在困难案例中偶尔出错，而算法一旦被找到规律，可能在同类输入上反复、稳定地犯错。
- 对抗算法既可能成为测试和防御工具，也可能成为更强的攻击工具；如果社会过度依赖 AI，原本的小漏洞就可能在关键领域变成现实风险。

### 26:08-29:32：智能化渗入日常生活

- 节目判断，未来五到十年可能出现与智能化相关的新一轮产业浪潮，动力来自更强的算力、更大的数据规模和算法自迭代速度。
- 这种变化不一定以“高出人类很多倍的机器人”突然出现，更可能通过无人系统、军工智能化、自动决策和各种软件服务一点点进入日常生活。
- 快递柜在开门状态不确定时追加确认电话的例子，说明现实系统会根据故障和攻击经验逐步增加校验环节，智能化往往是细节不断累积的结果。
- 主播认为数字时代既令人兴奋也令人恐惧：系统看似只增加了一点功能，却可能逐渐改变人们处理事务和承担责任的方式。

### 29:32-40:32：线上学术会议的组织困境

- 疫情使计算机、人工智能和通信等领域的年会集中转为线上，预录制一百多个论坛看似只是换一个会议工具，实际却暴露出生产流程和组织能力的问题。
- 学会统一采购 Zoom 账号并与会员系统打通，但登录、单用户功能限制、虚拟背景和使用习惯等细节，可能让资深演讲者直接放弃录制。
- 原本需要几位嘉宾同时在线的 Panel 难以凑齐，部分活动只能改成分别录制后再剪辑；主持、串场、录制时长和预约安排也都需要额外协调。
- 工具只能提供账号、录制和技术支持，会议流程、嘉宾配合、内容剪辑和观众互动仍需要组织者自己设计，线上活动并不会自动降低运营成本。
- 线上会议还要重新思考付费权益。让观众进入讲者交流群是一种新的售票方式，但是否真正改善参会体验，仍取决于内容、互动和服务设计。

### 40:32-46:48：用户体验与分布式开源年会

- 好的线上论坛需要从演讲人、出品人、志愿者和观众等不同角色出发，设计他们如何进入、操作、互动以及离开时带走什么，这本质上是用户旅程设计。
- 节目以开源社区年会为对照，认为技术社区不能只依靠行业牌子和知名讲者，还要考虑参会门槛、流程顺畅度和不同人群的实际体验。
- 开源年会通过开放城市报名，组织多个线下分会场，把活动分布到不同城市；这种分布式组织既让当地开发者建立联系，也降低单一线上主会场失败带来的风险。
- 互联网行业积累的用户思维和运营思维并不虚浮。它们与制造业、传统行业结合时，可以帮助面向大量用户的产品更好地理解需求、设计体验和组织服务。

### 46:50-54:12：开源奖项、运营与社区公信力

- 开源社区的评选活动有不同目的：表彰志愿者、向公众推荐值得关注的项目和人物，或为商业合作提供曝光；目标不同，评价方式和名称就应当明确区分。
- “开源先锋三十三人”被描述为圈内人的推荐，而不是声称存在一套客观评分、评出全国最优秀开源者；这种坦诚的定位反而更容易获得认可。
- 相比之下，如果名为“优秀开源技术团队”的奖项包含非技术团队或非开源团队，就会造成名不正、言不顺的争议。
- 技术、产品和运营是相互关联却各自独立的能力。一个人懂技术或开源理念，不代表他自然懂得用户、传播、奖项设计和社区运营。
- 活动、奖项和社区本身都可以被看作产品：如果既要获得商业收入又要积累口碑，就必须把赞助商、讲者和观众的体验纳入设计。

### 54:12-01:00:39：Rust、技术冲动与技术决策

- 节目讨论一篇“Rust 成为巨坑”的公司复盘文章，强调文章真正讨论的不是 Rust 语言优劣，而是技术与团队、产品和发展阶段是否匹配。
- 选择 Rust、迁移语言或重写系统，本质上都是技术决策；现实中通常存在多个可行方案，不能把某个热门技术包装成唯一正确答案。
- 技术媒体偏爱“我们用半年换掉某技术”的故事，技术主管也可能因为新技术能让自己的简历更好看，做出未经充分验证的选择，这就是简历驱动或个人偏好驱动的技术决策。
- 个人项目是可以尝试新语言和新工具的技术游乐场；公司则不是个人的游乐场，未经把握的技术冒险会把团队、成本和产品一起拖入风险。
- 学生用新工具自动化协作、记笔记和重复劳动是积极的探索，但个人实验与面向公司生产环境的技术承诺必须明确区分。

### 01:00:39-01:10:08：技术负责人和技术选型

- 技术负责人至少要同时关注技术团队培养、关键技术路线决策和工程项目成功；公司规模扩大后，这些职责可能分别由工程负责人、CTO、架构师或技术委员会承担。
- 大型组织更换技术路线会产生长期影响，不能由个人喜好或单次宣传独断决定；选型首先要回答它是否适合现有团队，而不是是否在社区里热门。
- Rust 的案例说明，团队规模扩大后，熟悉该语言的人才、标准库成熟度、文档数量和问题解决资源都可能成为现实成本。
- Rust 更强调安全可靠，可能适合产品稳定、迭代速度要求不高且愿意长期投入的团队；对需要快速试错、快速上线和快速修复的初创企业，学习和迁移成本可能超过收益。
- 技术选型应把技术本身和组织能力一起评估，不能把一个团队成功使用某技术的经验直接复制给另一个团队。

### 01:10:08-01:18:16：开放式软件工程与高校教育

- 节目认为，传统软件工程常把公司想象成一个封闭团队，但现代软件大量由自有代码、开源框架和第三方组件组合而成，因此需要“开放式软件工程”的视角。
- 选型不仅要看功能和性能，还要关注代码安全、漏洞、许可证、维护者性质、社区活跃度、版本生命周期、可替代性和服务承诺。
- 技术可以按核心框架与语言、一般性工具、关键业务工具等类别评估，不同类别对成熟度、替代方案、团队接受度和培训支持的权重不同。
- 学校虽然已经把 Git 和 GitHub 用于代码托管，却通常还没有充分讨论开放环境中的依赖管理、安全风险、社区治理、生命周期和组织责任。
- 大公司可能因为保守而不敢采用新技术，小团队则可能因为经验不足而随意选型；可靠决策需要客观指标与团队基础、培训能力、带头人支持等主观条件结合。

### 01:18:17-01:23:04：合理复用与课程考核

- 让学生为 C++ 课程制作完整在线教育平台，可能做出一个像样的系统，却未必考查了 C++ 课程真正需要的语言、标准库和面向对象能力。
- 工程教育不应一概要求学生从零实现所有东西。课程若考查算法思维，就应要求核心算法独立完成；课程若考查工程能力，就应允许并考查如何寻找、选择、组合和改造优秀的第三方实现。
- “聪明的抄袭”更准确地说是有边界、有理解、有验证的复用：学生要说明为什么使用现成组件、它解决了什么问题、还缺哪些部分，以及如何确保组合后的系统可靠。
- 节目认为，现代软件中第三方开源代码的比重已经很高，工程师能否正确选型和整合组件，本身就是重要的生产力。
- 学校可以利用新的微专业课程体系重新设计开放式软件工程教育，让课程目标、实践场景和评价标准真正对应未来行业的工作方式。

## 核心观点

1. AI 在常规输入上表现优秀，不等于在对抗性输入和关键场景中可靠；系统必须经过针对性测试，并保留清晰的人类责任边界。
2. 技术没有脱离场景的绝对优劣。技术选型必须同时考虑产品阶段、团队能力、维护成本、生态成熟度和失败后的替代路径。
3. 开源时代的软件工程不再只是编写自有代码，还包括第三方组件的选择、组合、安全、许可证、生命周期和长期维护。
4. 技术社区的活动和奖项也是产品，需要明确目标、区分角色、设计用户体验，并用恰当的名称和规则建立可信度。
5. 工程教育应考查真实能力：算法课程重视独立思考和实现，工程课程则应重视合理复用、选型整合、验证和对结果负责。
