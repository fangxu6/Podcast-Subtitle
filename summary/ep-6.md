## 内容摘要

本期先从上海封控期间的做饭、抢菜和社区生活聊起，然后介绍 2021 年图灵奖得主 Jack Dongarra。节目把他的工作放在高性能计算的发展史中解释：BLAS、LAPACK 等基础库和并行计算思想，把越来越强的硬件能力转化为普通程序和科学研究可以调用的计算能力，也支撑了 TOP500 等超算评测体系。

节目随后讨论 OpenBLAS、国产超算、MATLAB 受制裁后的替代方案，以及专业软件生态为什么难以迁移。嘉宾认为，普通应用可以快速重做，GitHub 这类平台也不是最需要恐慌的对象，真正需要长期投入的是超算、北斗、芯片制造和专业设计软件等“国之重器”。

最后讨论应用软件安全和开源参与。面对外部依赖，风险排序应先看代码漏洞和恶意软件，再看商业软件断供和平台封锁；与此同时，越担心被排除在国际社区之外，越应该主动参与、贡献和建立影响力。软件只有被真实用户持续使用，才能从一个粗糙项目成长为可靠的生态。

## 时间线

### 00:00-17:59：隔离生活与节目背景

- 上海封控期间，嘉宾分享做饭、抢菜、社区礼包、线上工作和在学校照顾学生的经历，也讨论居家隔离需要配套机制，不能只依赖个人自觉。
- 手头有什么食材、如何安排多顿饭，被调侃成一个逆向工程和优化问题：输入不是想买什么，而是已有资源如何支撑接下来的生活。
- 社区群中的疫情讨论容易从方案争论变成人身攻击。嘉宾认为，面对两千多万人规模的城市治理，普通人能做的是配合不断调整的策略，并保持对现实困难的理解。
- 这些生活片段引出节目的主线：复杂系统、科学计算和软件安全，都需要把现实约束、资源和风险纳入设计，而不是只讨论抽象技术。

### 17:59-26:57：图灵奖与高性能计算的基础

- 2021 年图灵奖首次颁给高性能计算领域的 Jack Dongarra。高性能计算不仅体现国家计算能力，也推动了科学研究和工程应用的发展。
- 硬件性能遵循摩尔定律不断增长，但软件未必能自动利用新增算力；超算领域的并行算法和数值计算库，正是把硬件潜力转化为可用能力的关键。
- BLAS 将向量、矩阵等基础运算定义成通用接口，上层算法只需遵循接口，底层库就能针对不同硬件进行优化；这为之后的多种实现和软件生态提供了抽象层。
- 相关算法从军方和科研计算扩展到生物制药、天气预报、航空等领域，并通过 LAPACK 等基准和工具影响了普通计算机与科学软件。
- TOP500 使用这些标准化基准评测超级计算机，天河、太湖之光和日本富岳等系统的排名，成为公众理解超算竞争的一个窗口。

### 26:57-32:39：超算排名、资源与 OpenBLAS

- 不能只看 TOP500 前几名判断国家超算实力，还要看上榜机器的总算力，以及尚未完全公开或投入运行的下一代系统。
- 高校和科研机构可以申请超算资源，但超算更适合密集型数据分析、预测和模型计算，不是把普通业务系统整体搬上去运行。
- 超算中心需要大量投入和电力成本，因此会希望计算资源真正服务于科研和产业，并产生可验证的应用价值。
- OpenBLAS 是国内开发者张先亿基于 BLAS 规范开发的开源实现，在国际超算领域使用广泛；有人因为地缘政治试图限制它支持某些芯片，反而说明不了解开放接口和多种底层实现之间的关系。

### 32:39-43:39：国产超算与 MATLAB 迁移成本

- BLAS 是接口协议，不是单一实现。同一个应用可以使用通用的 OpenBLAS，也可以根据硬件切换到 NVIDIA 等厂商的优化实现，而上层代码无需全部重写。
- 美国对超算芯片和高校软件授权的限制，推动中国建设使用国产芯片的太湖之光等系统，但超算设计软件、代工和完整软件栈仍存在国产化不足。
- MATLAB 由早期教学和数值计算工具发展成广泛的软件生态，涵盖大量学科、文件格式、插件、硬件和后处理工具；成熟生态让替换成本不只是一套语法的学习成本。
- GNU Octave、Scilab 和 Python 科学计算生态提供了不同程度的替代方案，有些能兼容 MATLAB 文件或语言模块，但迁移仍需要时间、决心和组织执行力。
- 公司内部如果因合规和信息安全要求停用某软件，真正困难的不是宣布禁用，而是投入足够人力开发替代品并兼容原有插件和库。

### 43:39-54:31：软件安全的风险排序与开源参与

- 面对外部软件依赖，较合理的顺序是：首先防范代码漏洞和普通安全缺陷，其次防范恶意软件或政治投毒，再考虑商业软件断供，最后才是 GitHub 等平台彻底关闭入口。
- 风险排序决定资源投入。不能因为最戏剧化的“突然不能用”最容易传播，就把所有应用都提前重做，而忽略日常发生概率更高的漏洞和供应链问题。
- 与其只担心国际社区会排除中国开发者，不如主动参与有影响力的开源项目，提高贡献比例、技术能力和社区影响力；参与过真实协作的人，即使平台变化，也更有能力继续工作。
- 俄罗斯拥有不少高水平开发者和开源贡献，中国近年来已有进步，但仍需要更多学生、教师和研究团队走进国际社区，认识优秀项目并建立真实连接。
- 国内自发起的开源项目也需要真实用户持续使用、反馈和改进。软件不是靠少数高手一次写完，而是在使用中逐渐形成可靠产品和生态。

### 54:31-01:02:11：三类软件与“国之重器”

- 日常功能型应用通常不构成长期断供风险，需求出现时可以较快重做；GitHub、GitLab 这类平台即使面临极端情况，也可以利用 Git 的分布式特性锁定版本和 fork 内容。
- 真正需要提前布局的是超算、北斗、芯片制造全流程及其专业软件。这些工具用户少、领域窄、迭代周期长，无法在危机发生后临时复制出好用的替代品。
- MATLAB 这类专业工具可以从学校教学中逐步引入开源替代，让新用户不必先建立对旧软件的依赖，再通过真实使用培育生态。
- 软件选择应区分开源与闭源，而不能简单按“美国软件”或“西方软件”划线。成熟的开源项目值得使用，也值得积极贡献和争取社区影响力。
- 软件安全既需要国家层面的规划，也需要高校、企业、开源社区和真实用户共同参与；开放协作和可靠的供应链准备可以同时存在。

## 核心观点

1. 高性能计算的价值不只在于制造更大的机器，更在于用标准化接口、并行算法和基础库把硬件能力转化为可复用的软件能力。
2. 专业软件的替代难点在生态、插件、硬件和长期使用积累；迁移不是宣布禁用，而是持续建设和验证新的工作流。
3. 软件安全应按发生概率和影响排序，代码漏洞与供应链缺陷通常比极端的全面断供更值得优先处理。
4. 越担心被国际社区排除，越需要主动参与开源协作；贡献、使用和影响力本身就是降低依赖风险的方式。
5. 日常应用、平台软件和关键产业软件的风险不同，应采用不同的准备策略，不能用一套“全部国产化”的口号替代具体分析。
