# 第106期 Rust语言要干掉谁

- SRT 条目：696

## 内容摘要

本期从 2001 年中美南海撞机事件的纪念日谈起，回顾王伟牺牲、美军 EP-3 迫降陵水机场、外交交涉以及飞机拆解运回等经过，并指出常见宣传材料中关于飞机编号的误传。随后讨论《流浪地球 2》在日本上映时的反响和配音问题，以及小米 SU7 的定价、品牌号召力和首批交付口碑。

节目还比较美国巴尔的摩大桥与广东撞桥事故的结构差异，说明连续钢结构在局部受损后可能引发整体坍塌；接着从墨天轮等评测和实际案例讨论国产数据库，认为信创替代既是现实的安全需求，也需要区分高敏感低负载场景与银行、电力、交通等高可靠场景，采用循序渐进的迁移方式。

后半段集中讨论 Rust。节目认为 Rust 的安全性、性能和工具链使它在高性能命令行工具、WebAssembly 以及部分 C++ 场景中有机会，但语言选择不能只看新奇和宣传，还要考虑生态、任务、团队经验与管理方式。Rust 编译器能提前发现大量问题，却不能消除所有运行时错误；它适合工程基础较深、愿意沟通和投入学习的团队，不适合作为不加筛选的通用答案。

## 时间线

### 00:00-11:37：南海撞机事件与事实辨析

- 节目在 4 月 1 日回顾 2001 年中美南海撞机事件：王伟驾驶歼-8II 与执行侦察任务的美军 EP-3 相撞，跳伞后失踪并被认为已经牺牲；EP-3 随后迫降海南陵水机场，机组人员被控制。
- 当时南海方向的部署、搜救和记录手段都比较有限，双方对碰撞经过缺少足够硬的物证。节目以此感叹今天有更多有人和无人平台可以留下完整证据。
- 事件后来演变为持续数月的外交交涉：美国先拒绝正式道歉，最终以 `very sorry` 的表述作出有限让步；24 名机组人员被放回，美方也接受把飞机拆解后用租来的大型运输机运回，而不是完整飞走。
- 节目提到，杨洁篪当时作为驻美大使登上 CNN 解释事件，帮助美国舆论理解“军事飞机进入他国附近并导致人员死亡”的背景；同时指出，常见材料把涉事飞机编号写成 8192，节目认为实际出事的是 8194，前者是王伟此前执行类似任务时驾驶的另一架飞机。

### 11:37-19:27：《流浪地球 2》的日本上映

- 《流浪地球 2》在日本延迟一年多上映，节目认为日本观众对科幻、悬疑和推理有较强兴趣，影片在当地也投入了配音和宣传，获得了比北美、欧洲更充分的传播条件。
- 日本观众对刘德华和马兆这个角色的关注尤其明显；一位硬科幻爱好者首映后写出近万字影评，节目据此认为东亚文化背景可能帮助观众理解影片的设定和情绪。
- 讨论重点转向国际发行中的本地化取舍。影片原本通过不同国家使用各自语言、再借助自动翻译来表现全人类合作，但欧洲发行时曾被要求把所有语言统一配成当地语言，削弱了原有的世界观表达。
- 节目认为中国作品出海需要先找到能准确理解其创作重点的市场，再逐步扩大传播范围；所谓成熟市场并不必然最早接受新作品。

### 19:27-26:29：小米 SU7 的市场进入

- 小米 SU7 的价格没有低到制造轰动，却以配置而言比较亲民；节目转述一些分析认为它可能在亏损销售，但也承认是否真的亏损尚不确定，后续降本空间和生态收益仍需观察。
- 小米拥有较大的用户基础和品牌忠诚度，预订情况因此较好；真正决定产品成色的将是交付质量、售后服务和首批车主的真实反馈，而不是发布会或厂家控制的媒体评价。
- 主播结合小米净水器的经历，认为小米曾通过较低价格、自助服务和更扁平的互联网化管理改变传统家电服务，这种消费电子和供应链经验使其造车具有不同于传统车企的亲和力。
- SU7 直接进入 20 万至 30 万元、竞争激烈的智能车市场，节目倾向于建议等待首批交付和更多真实评测，再判断它是否值得购买。

### 26:29-36:15：巴尔的摩大桥事故与结构风险

- 节目把美国巴尔的摩大桥被船撞后整体坍塌，与广东一座桥被船撞后局部桥面坍塌的事故放在一起比较，指出两起事故的时间、人员伤亡和结构形式都不同。
- 广东桥采用分段的混凝土桥墩和桥面结构，局部结构受损时影响相对容易被隔离；巴尔的摩大桥是连续钢结构，关键支撑点失效后，受力变化沿整体结构传递，形成类似多米诺骨牌的连锁坍塌。
- 连续结构的优点是用料较省、外形简洁，但代价是缺少局部风险隔离。节目认为，既然桥下长期通行大型船只，就应考虑防撞屏障、缓冲或引导船只偏移等额外防护。
- 节目还澄清网上“装满中国货物的船撞了美国大桥”的图片很可能是后期编造的说法：船只注册地、船员来源和货物来源不能被简单等同，不能用未经核实的中国因素替代对事故责任和工程设计的分析。

### 36:15-54:37：国产数据库的现状与替代路径

- 节目推荐通过墨天轮了解国产数据库，其资料既包含吞吐量、功能和数据处理能力等技术指标，也包含商业模式、专利、资质和应用案例等市场信息。
- 讨论认为，OceanBase、TiDB、华为 openGauss 等头部产品背后有大厂或长期专业投入，在高校评测、课程合作、科研部署和金融等实际场景中已经形成一定积累；国产数据库不再是过去那种选择极少的状态。
- 信创和安可市场体现了建立自主替代能力的现实需求，但“大量产品涌入”也会带来泥沙俱下的问题。银行等高频交易和海量数据场景不可能随意替换，真正进入这些场景的产品必须经过长期稳定性和可靠性考验。
- 节目把迁移场景分成两类：军队、国家安全等数据高度敏感但业务负载相对有限的系统，可以优先考虑可控、可信的国产替代；银行、电信、电力、交通等既敏感又不能中断的系统，则应先从非核心业务开始，逐步验证后再扩大范围。
- 国产数据库要挑战关键行业，除了获得试用机会，也需要面对银行长期使用 IBM 封闭体系、后来逐渐转向 Oracle 等成熟生态形成的高门槛；替代不是一次性运动，而是持续投入、案例积累和分层推进的过程。

### 54:37-01:00:22：Rust 的热度与采用风险

- Rust 近年频繁出现在系统、前端工具链和安全编程的讨论中，节目把“Rust 会不会替代某种语言”视为一个需要拆开的问题，而不是根据热度直接下结论。
- 开源软件并不意味着一定能提高研发效率。节目认可应避免团队因为个人偏好采用小众、未成熟、生态不完整的技术；产品经理最难处理的情况，就是研发一会儿宣称新技术很强，一会儿又以技术太新为由说功能无法实现。
- Rust 的正式稳定版本发布于 2015 年，虽然从出现到现在已有较长时间，但总体仍属于相对年轻的技术。节目建议对狂热拥护者的宣传保持距离，亲自做小规模验证，了解语言真正擅长什么、代价是什么。
- Rust 适合有较深工程和编程基础、熟悉多种语言、愿意通过沟通解决复杂问题的团队；经历磨合后，它可能在某些项目中比 C++ 有更高生产力，但团队条件不足时应谨慎采用。

### 01:00:22-01:10:09：Mozilla、浏览器与 WebAssembly

- Rust 起源于 Mozilla 的技术体系。Mozilla 认为浏览器已经越来越像一个操作系统：它要负责 GPU 页面渲染，也要在虚拟机中运行 JavaScript，因此需要一种能够控制底层代码质量和内存问题的语言。
- Rust 的静态类型、强类型和编译期检查等特征，部分源于对 JavaScript 生态和浏览器底层可靠性的反思。它后来常被用于重写打包、预编译、依赖管理等高性能命令行工具，但这更像生产力工具升级，不等同于前端编程本身被 Rust 改写。
- WebAssembly 是与语言无关的二进制中间格式，任何合适的语言都可以编译到浏览器虚拟机中运行。Rust 可以编译到 WebAssembly，MoonBit 等语言也可以针对这一环境优化，因此 WebAssembly 并不天然属于 Rust。
- 是否使用 Rust 取决于性能、工具链和团队习惯。如果 C、C++ 或其他语言已经能解决问题，就没有必要仅因为 Rust 流行而更换；真正重要的是运行环境、生态和交付目标。

### 01:10:10-01:20:19：Rust、C++、Java 与生态壁垒

- C 仍然承担接近汇编、直接面向嵌入式硬件和极致实时性能的职责，这部分很难被 Rust 完全替代；Rust 更直接的竞争对象是传统 C++ 的部分应用场景。
- C++ 在重型桌面应用、操作系统、浏览器、游戏客户端和网络游戏服务端拥有长期积累。Rust 可能在重并发的后端服务等场景提供替代机会，但节目当时还没有看到这种替代已经形成普遍趋势。
- Java 的优势不只是语法，而是庞大的用户群、稳定的社区、成熟的库和 JVM。工作流、报表等需要大量人员协作和复杂业务定制的系统，仍然适合利用 Java 的生态；短期内 Rust 很难撼动这些基础。
- 语言的语法和运行时生态可以分开：Clojure、Scala、Kotlin 等 JVM 语言能复用 Java 的库和运行环境，ClojureScript 也能把熟悉的语法编译成 JavaScript。真正不可替代的往往是生态、库和已有经验，而不是表面语法。

### 01:20:19-01:30:29：语言选择取决于任务和团队

- 评价语言要先问任务是什么、由什么样的人完成。语言越灵活，越需要技术负责人判断团队能否自律、是否需要限制危险特性，以及成员是否有能力把自由度转化为有效创新。
- Ruby 等语言的元编程和开放能力既可能提高表达力，也可能成为维护风险；解决办法不只是换语言，还包括团队约定、权限边界和对高级特性的管理。Rust 的学习和使用同样需要把技术选择与团队治理放在一起考虑。
- Rust 编译通过并不意味着程序不会有运行时错误。Rust 编译器和 Rust Analyzer 能通过静态分析提前发现大量问题，某些数据库库甚至可以在开发阶段检查 SQL 与数据库字段，但这些能力背后依赖工具和库作者长期投入，不能被夸大成绝对保证。
- 节目还讨论以 Rust 编写数据结构和算法教材的现象。Rust 的泛型、所有权等概念会占用大量学习成本；如果教学目标是抽象、数据和编程逻辑，过于陡峭的语言可能让学生把时间花在语言细节上。教学语言应服务于教学目标，而不是只追求新奇。

### 01:30:29-01:33:01：Rust 话题的收束

- 节目总结认为，Rust 是值得持续关注和实践的语言，但它不会凭借单一优势消灭所有旧语言。它更可能先在对安全、性能和工具链有明确需求的局部场景中扩大影响。
- 选择学习语言时，可以先用较简单、低认知负担的语言掌握抽象和编程基础，再根据实际任务学习 Rust 等更复杂的工具；学习者不必拒绝新语言，但教育者应帮助他们减少不必要的弯路。
- 主播承认编程语言涉及的技术、生态和人的因素很多，一次节目无法讲完，后续仍可能继续讨论。

## 核心观点

1. 技术替代不是口号。Rust 的性能和安全性确实带来机会，但能否替代 C++ 或挤压 JavaScript 的部分场景，取决于具体任务、工具链和生态，而不是语言热度。
2. 关键系统的国产替代需要分层推进。高敏感低负载场景可以优先尝试，高可靠高负载系统则必须从非核心业务开始，以稳定性、案例和可维护性逐步建立信任。
3. 工程设计要正视风险传播。连续桥梁结构、软件依赖和语言的自由度都有类似问题：平时效率较高，但关键节点失效时可能把局部问题放大为整体事故。
4. 编程语言选择本质上也是团队管理选择。技术负责人的判断应包括成员经验、沟通方式、纪律和可接受的学习成本，而不只是语言本身的功能列表。
5. 编译器和工具能提前发现很多问题，却不能替代测试、审查和责任边界。越复杂的技术，越需要用真实任务验证其收益，并明确谁负责最终结果。
