# 第107期 重构还是重写

## 内容摘要

本期先从以色列袭击世界中央厨房（WCK）援助车队谈起，讨论这起事件为何比中东地区通常的冲突更容易触发美国和其他英语国家的政治压力，也指出美国一边谴责袭击、一边继续提供武器的矛盾。随后节目转向 XZ 供应链投毒事件和 Microsoft Teams 与 FFmpeg 社区的交涉，讨论开源软件的安全责任、资金来源、免费搭车和身份验证等问题。

节目中段用“Python 内置排序为什么比手写快速排序快”说明标准库、编译器、底层实现和算法知识的重要性，同时提醒对工具保持谦逊不能变成不求甚解。主体话题是一个大型职业社交网站的前端迁移：面对数百万行遗留代码和过长构建时间，节目比较五年渐进迁移与较短周期重写的利弊，并延伸到前后端分工、全栈能力、用户沟通和技术决策。

最后讨论一位普通高校学生希望用开源连接学校与企业的想法。节目认为，比赛和学历评价不一定能代表实战能力，开源项目可以补足高校实践教学，但学校、基金会和企业都需要投入并承担责任。对个人而言，可以从基础工具和阅读成熟项目开始，逐步运行、修改、贡献，最终成为社区成员或发起自己的项目。

## 时间线

### 00:00-10:00：WCK 援助车队遇袭与政治压力

- 节目介绍世界中央厨房（World Central Kitchen，WCK）：组织由一位拉丁裔美国厨师于 2010 年创建，核心理念是食物属于基本人权，救援对象不应因政治立场而被区别对待。
- 以色列袭击 WCK 车队造成 7 人死亡，死者来自澳大利亚、巴勒斯坦、波兰、英国以及美国和加拿大等国家。节目认为，死者中有多个英语国家公民，使这起事件在美国、英国、加拿大和澳大利亚引发了格外强烈的反应。
- 节目把袭击伊朗驻叙利亚使馆和袭击 WCK 区分开：前者被主播推测为试图把伊朗拉入战争，后者更像是以色列判断失误或行动失控，但两件事的后果都需要继续观察。
- 美国政府在舆论压力下要求以色列保障平民和国际组织安全，特朗普也批评以色列总理处理得太糟，却没有因此表示不再支持以色列。节目同时指出，美国政府一边谴责袭击，一边继续出售高爆炸弹，实际行动与公开表态之间存在明显矛盾。

### 10:00-20:28：XZ 投毒与事实、推测的边界

- XZ 是广泛使用的压缩解压基础库。节目介绍，一名已经在社区贡献一年多、逐渐取得信任的账号，在某个版本中加入了隐藏在测试数据文件里的恶意代码；由于依赖范围很广，这起供应链投毒的潜在影响尤其严重。
- 节目不接受仅凭账号名字判断攻击者身份或来源，认为目前至少存在两种解释：贡献者长期潜伏后主动投毒，或正常贡献者的账号被盗用。恶意提交时间与账号原有作息不一致，也被视为账号被盗的可能线索，但不能直接得出结论。
- 从补丁提交、催促项目放权到推动更多发行版接纳 XZ 的过程看，攻击者的行为既可以解释成热心的社区贡献，也可以解释成长期铺垫的潜伏行动。正因为正常行为与恶意行为高度相似，开源社区很难只靠表面活动识别风险。
- 节目批评把用户名、国籍猜测或未经核实的故事当成事实传播，认为面对供应链事件时应先复原可确认的时间线，再把推测和评论分开。

### 20:28-31:43：FFmpeg 交涉与开源叙事的失真

- Microsoft Teams 的员工曾向 FFmpeg 社区报告一个紧急问题，但节目判断这更接近新旧版本行为变化而文档说明不清，并非必须由上游立即修复的严重缺陷；问题本身后来基本得到解决。
- 中文网络转述把原本简短的交流扩写成“大公司白嫖开源项目”，还加入长期维护合同和几千美元一次性付款等原始记录中没有的内容。节目以此说明，翻译、转述和评论混在一起时，很容易让读者误把观点当成事实。
- FFmpeg 账号把 XZ 事件归因于志愿者缺乏资金，节目认为这也可能混淆了因果：XZ 更像是有组织的长期攻击，不能简单归结为“给开源项目更多钱”就能避免。
- 企业员工在公开社区中表达个人项目的紧迫性，也可能无意间给所属公司制造公关问题。大型企业有能力自行提交补丁或采用替代方案，不应把自己的内部优先级直接转化成社区必须承担的优先级。

### 31:43-42:05：开源供应链的公共责任

- 开源代码从压缩、加密、网络通信到前端依赖，已经成为软件基础设施的一部分。问题在于，维护者承担了安全维护的压力，而使用者未必愿意为公共收益投入同等的资金、人力和代码审查。
- 节目用“免费搭车”解释企业的普遍选择：漏洞修复后所有用户都会受益，但单个企业往往只愿意处理已经暴露在自己面前的风险，不愿为整个生态预防尚未发生的问题。
- 大型公司确实会向 OpenSSF、OpenChain 等供应链安全组织投入，但现有资金和专业力量仍不足以覆盖数量庞大的关键依赖。政府提高企业安全责任可能增加投入，同时也可能把风险和合规成本推到抑制创新的程度，这是一种需要权衡的政策选择。
- AI 可能让攻击者更容易伪造多个看似真实的开发者账号、模仿社区成员的表达并协同推进代码提交。Sigstore 等签名机制试图在供应链环节建立可验证身份，但强制签名也会增加贡献门槛，安全与开放之间仍有代价。

### 42:05-54:05：Python 排序、标准库与工程谦逊

- 节目从“Python 内置 `sort` 为什么比自己写的快速排序快一百倍”展开：内置排序使用经过长期优化的算法，能够稳定地保持 `O(n log n)` 级别的性能，而手写快速排序还可能因为基准值选择不佳退化。
- Python 的内置函数底层由 C 实现，并经过编译器和大量工程实践优化；NumPy 等常用库也把数组、矩阵运算等耗时部分放在高效的 C 代码中，所以不能把一段教学代码与成熟底层库直接比较。
- 节目总结了两组相反的“程序员错觉”：一组认为自己能胜过标准库、编译器和内存管理，另一组认为标准库绝不会错、编译器绝不会出错、自己永远不配管理内存。后者的危害通常较小，但两者都不是绝对正确。
- 使用成熟工具可以把精力留给业务和自己真正能驾驭的问题，但不能因此停止成长。程序员仍应通过定位系统级问题、理解底层实现和验证性能来扩大能力边界。

### 54:05-01:04:56：大型前端系统该重构还是重写

- 节目讨论 LinkedIn 一篇关于前端迁移的文章：网站前端积累了约两三百万行代码，构建时间达到 17 分钟，技术负责人提出用五年时间从 AngularJS 逐步迁移到 React；另一团队则主张采用更彻底的重写方案。
- 五年迁移计划的问题不只是周期太长。五年后的 React、前端生态和业务需求都可能变化，长期迁移会持续占用团队资源，拖累新功能开发，也让团队长期背负旧系统和迁移系统并存的压力。
- 节目认为，如果系统已经到了不改不可的程度，技术部门应尽快行动；具体选择渐进式迁移还是重写，要看团队能力、依赖关系、用户需求和新旧系统并存方式，但一般企业的这类工程最好在一至两年内完成。
- 对前端项目而言，稳定的后端 API、明确的产品规格、持续的用户使用和较强的可测试性，使重写比重型后端更容易控制。重写并非天然正确，但在边界清楚、功能可枚举的前端系统中可能比逐行修补遗留代码更可靠。

### 01:04:56-01:16:22：前后端分工与全栈能力

- 节目反驳“后端更稳定、职业发展一定更好”的直觉：后端达到较高水平需要更长时间和更多真实经验，前端虽然变化快、入门相对容易，但人才需求量通常更大。
- 前端的需求会随着市场、用户、产品经理和老板的想法不断变化，因而更适合快速迭代和模块级验证；后端则需要更资深的人设计稳定的框架、数据和服务边界。
- 给学生和新人更实际的建议是先做全站程序员，至少亲自接触数据库设计、基本业务逻辑、API 和用户交互，而不要长期只做某一层的狭窄螺丝钉。完整链条能提高可塑性，也能让人理解上下游的代价。
- 技术职位越往上越离不开人与业务。后端架构师需要理解需求并说服他人，前端开发者需要具备用户感和与产品经理谈判的能力；只会调用 API 或堆砌流行架构，都不足以证明技术决策正确。

### 01:16:22-01:26:59：开源经历与高校评价体系

- 节目介绍一位普通高校大四学生的困惑：学校和教师更重视教育部门白名单中的标准化竞赛，而学生认为真正能在开源社区贡献代码、获得社区认可的人，往往拥有更强的实战能力，却不容易得到学校评价体系的承认。
- 竞赛可以训练解题和规范化题型，但不一定等于实际项目能力。开源项目要求参与者处理真实需求、读懂既有代码、与陌生开发者协作，这些经验也更容易被企业直接观察到。
- 基金会可以尝试联合高校和企业设计开源毕业课题，让企业提供题目和导师，再通过公开答辩、推荐信等方式帮助优秀学生获得机会；但学校不愿把毕业设计交给风险更高的新模式，大厂也不愿在没有深度参与的比赛上投入筛选和培养成本。
- 因此，开源评价若想进入学校体系，可能仍需教育部门认可的白名单；若不依赖学校背书，学生就只能通过企业招聘、社区声誉或自己做出成果来获得社会认可。

### 01:26:59-01:39:38：从阅读代码到成为社区成员

- 节目推荐一条循序渐进的学习路径：先掌握版本管理、包管理和语言环境，再挑选合适的开源项目，阅读文档与目录结构，跑通项目主线，然后尝试修改、提交贡献，最后再考虑发起自己的项目。
- 这条路径训练的不只是看代码、写代码和改代码，还包括写邮件、提 Issue、发 Pull Request、请求代码审查、遵守社区规则以及与维护者建立正常协作关系等软技能。
- 开源项目可以补足高校实践教学的不足：它提供真实而持续维护的项目、企业导师和社区伙伴，也给非名校学生接触前沿技术和真实协作的机会。但要把开源变成稳定的学习园地，学校或组织仍需长期运营和筛选合适的入门任务。
- 节目提出“游泳池”的比喻：有些人可以直接进入复杂社区学习，另一些人需要一个有教练、深度适中且不会立刻把人淹没的教学项目。持续维护的文档项目、案例库或其他低门槛但有深度的开源项目，可能成为这种通用启蒙园地。

## 核心观点

1. 开源软件已经承担了公共基础设施的角色，但安全收益具有公共品属性，不能只在事故发生后要求志愿者负责；企业、基金会和政府都需要承担相应的投入与治理责任。
2. 技术讨论必须把事实、推测和评论分开。供应链攻击的身份猜测、社区交涉的网络转述以及企业员工的优先级，都不能替代对原始时间线和真实需求的核对。
3. 使用成熟标准库和工具是工程能力的一部分，但“相信工具”不等于放弃理解和验证。谦逊可以降低无谓风险，持续追问底层原理才能避免能力停滞。
4. 重构还是重写没有通用答案，关键在于系统边界、团队能力、迁移周期、可测试性和新旧系统并存方案。前端在稳定 API 和明确规格支撑下更容易重写，但这不能推广到所有遗留系统。
5. 软件职业成长不应局限于单一技术岗位。理解完整交付链条、与用户和产品沟通、参与真实开源项目，往往比只刷题或只维护一层代码更能建立长期能力。
