## 内容摘要

本期先从微软用 Go 重写 TypeScript 工具链谈起，讨论“移植”和“重写”的区别，以及工程团队为什么会根据工作量、语言特征和垃圾回收等实际约束选择 Go，而不是因为 Rust 的流行度就采用 Rust。随后节目转向 MCP、Function Calling 和 Agent 框架，梳理大模型调用外部工具的基本流程，并讨论 MCP 的 server 架构、双向通信、长连接和标准化愿景带来的复杂度。

中段讨论特朗普执政最初 50 天的关税、对外政策、马斯克及美国全球战略收缩等新闻。之后进入“随缘编程”话题，区分让 AI 直接生成代码、由人审查的 AI 辅助编程，以及更接近“只描述需求、看着代码自动出现”的随缘编程。节目结合阅读代码、生成 README、实现框架和修复 Bug 的经历，认为任务越具体、人的理解越充分，AI 越容易产出可靠结果；成熟流程中的小函数和胶水代码更适合交给 AI，复杂架构和探索性问题仍需要人的判断。

后半段讨论普通人如何参与开源，从免费使用、自由修改和自由分发谈到提 Issue、回答问题、修复 Bug、提交 Pull Request，以及连接不同社区的贡献。节目还把 Git 仓库用于课程分组、论文协作和记录个人分工，作为开放协同的实践。最后是读书环节，推荐《机器学习系统设计》《编舟记》和江户川乱步的《诡计集成》，分别讨论 AI 系统中的数据与模型、词典编辑工作的严谨与热爱，以及推理小说诡计分类和人物叙事的关系。

## 时间线

### 00:00-05:16：微软用 Go 重写 TypeScript 工具链

- 微软团队为了改善 TypeScript 工具链的性能，用 Go 在不到一年内完成了移植，速度获得了数量级提升；这也引发了 Rust 爱好者关于“为什么不用 Rust”的讨论。
- 节目区分了“移植”和“重写”：Go 与原有 JavaScript 工具链在语言特征和垃圾回收机制上更容易对应，很多代码可以按原结构迁移；Rust 的设计理念差异更大，使用它往往意味着真正重新设计和实现。
- Rust 很适合高性能命令行工具，像 UV 就替代了 Python 生态中的部分工具链，但语言选择应服从项目的工作量、维护成本和实际目标，而不是变成技术立场之争。

### 05:16-15:45：从 Function Calling 到 MCP

- Function Calling 的基本流程是：把可用工具及参数描述交给模型，模型返回想调用的函数和参数，由应用程序实际执行，再把工具结果放回上下文，让模型生成最终回答。
- 模型本身并不直接运行程序，工具调用的执行、结果封装和下一次模型请求，都需要宿主应用完成；不同模型在工具选择和参数格式上仍可能存在差异。
- MCP 在类似流程上增加了 MCP server 和 client 的协议层，希望把工具实现标准化，让同一个 server 能被不同的 IDE 或 Agent 环境复用。
- 节目认为，MCP 的标准化方向有价值，但其通信结构和协议细节比直接调用函数复杂，理解和实现成本也更高。

### 15:45-26:35：MCP 的复杂度与 Agent 框架生态

- MCP 不只描述函数调用，还把与大模型交互有关的消息参数带入工具协议，并要求 client 与 server 保持长连接，这会增加部署和架构设计的约束。
- MCP server 的数量和实际使用规模可能没有社交媒体讨论显示得那么大；如果要成为事实标准，还需要降低双向通信等机制的复杂度和实现门槛。
- 节目把 Agent 应用开发看作正在形成的新生态，底层需要模型与工具之间的兼容接口，类似过去移动平台中的 SDK 和应用商店所承担的基础作用。
- 现有框架各有优缺点：有的预置了大量 Agent，有的强调简洁编排，有的提供类型检查和可观测性，但还没有一个框架足够成熟，能让开发者完全放心地用于生产环境。

### 26:35-41:51：特朗普执政 50 天的新闻与美国对外政策

- 节目回顾特朗普执政最初 50 天的高密度新闻，重点讨论加征关税、加拿大和欧盟的反制、巴拿马运河权益，以及中美贸易摩擦可能对供应商和美国日常消费品价格造成的影响。
- 节目还讨论马斯克推动削减政府部门的做法及其在美国国内引发的反应，并把相关争议放在技术圈的无政府主义、政府效率和公共部门职能等问题下观察。
- 关于美国全球战略，节目提到美国是否会减少对台湾和西太平洋的战略投入，以及半导体供应链向美国、日本和欧洲分散后，台湾在美国战略中的作用是否发生变化。
- 俄乌停火倡议也是讨论的一部分。节目认为停火条件、各方目标和外交团队的执行经验之间存在张力，后续走向仍取决于各方谈判和外部局势。

### 41:51-53:49：什么是“随缘编程”

- “vibe coding”被节目译作“随缘编程”：用户不再认真思考和编写每一部分代码，而是描述想法、让工具生成代码，然后在代码运行时体验一种自动流动的编程节奏。
- 这和正常的 AI 辅助编程不同。后者仍由人提出问题、审查方案、选择实现并修改代码，AI 是工具；随缘编程更接近“你看着办，能不能成随缘”。
- 节目分享了使用 Roo Code、Aider 等工具阅读 MCP 示例、生成 README 和尝试搭建 Ruby 大模型框架的经历。AI 阅读已有代码和生成文档很有效，但直接按 README 生成完整框架时，常常连基本运行都无法保证。
- “随缘编程”在简单页面或套路化小游戏等场景中可能看起来效果很好，但这类演示不能代表复杂、差异化、需要长期维护的软件系统。

### 53:49-01:07:34：AI 编程的边界、低代码与教育

- AI 修复复杂 Bug 时容易反复试错，甚至破坏原本正确的部分；当人能明确指出具体函数、触发条件和预期修复方式时，模型的成功率会明显提高。
- 已经成熟的业务流程、短小函数和胶水代码更适合 AI 生成。若接口、输入输出和数据访问规范已经确定，AI 可以较快完成组合式操作；仍处在探索阶段的框架设计和架构问题，则需要人先想清楚。
- 节目认为，AI 可能优先影响重复性强、主要负责拼接已有模块的工作，而规划、架构、探索和需要独特设计的任务仍然依赖人的理解。正确提问和判断结果优劣，都需要相应领域的积累。
- 在教育中，不能只让学生重复人类已经解决过的题目。节目倾向于让学生从真实需求出发，关注思考和实践过程，并尝试用 AI 辅助设计跨学科课程和开放性问题。

### 01:07:34-01:20:06：普通人如何参与开源

- 对许多用户来说，开源首先意味着可以免费使用；但自由软件的范围还包括自由修改、自由分发，以及修改后继续分发。正是这些自由让用户能够从使用者逐步进入社区。
- 普通人不一定要先会写大量代码，清楚报告版本、错误信息、操作系统、语言版本和复现步骤，就是对开源项目有价值的贡献。
- 进一步的参与包括本地修复 Bug、提供规避方案、回答其他用户的问题、提出功能方向，以及把修改通过 Pull Request 反馈给上游。节目强调“upstream first”，让更多下游用户共享修复。
- 节目分享了一个 Emacs 插件问题的案例：通过同时向插件社区和配置框架社区提 Issue，把两个原本联系不多的社区连接起来，最终帮助开发者定位问题并修复。

### 01:20:06-01:33:08：开源回馈与开放协同

- “人人为我”很容易理解，真正维持社区的是“我为人人”的回馈。提问、回答、修复、文档、想法和社区沟通都可以构成贡献，不必等到能写大型功能才开始参与。
- 小公司不必为了“开源”这个名义而开源，是否参与应当和商业模式、生态推广、产品传播或个人项目目标结合起来；没有清晰目标时，做好普通用户或个人项目也足够。
- 个人可以把博客、学习和日常工作连接到开源仓库；课程、论文和团队项目也可以通过 Issue、文档、代码、测试和部署记录来组织分工。
- 节目把仓库中的实际提交称为一种“Proof of Work”：设计、测试、部署等非编码工作也应该留下可观察的成果，以减少小组协作中的搭便车问题。

### 01:33:08-01:44:31：《机器学习系统设计》

- 这本书面向有编程和软件开发基础、希望构建 AI 或机器学习系统的读者，重点不是入门算法，而是完整的系统实践。
- 内容覆盖数据工程、训练数据、特征工程、模型开发、模型评估、模型部署、预测、生产环境中的持续学习与测试，以及 MLOps、可信 AI 和价值对齐。
- 与传统软件工程相比，机器学习系统的性能越来越取决于数据和模型，而不只是代码、算法和软件流程。知识库、数据格式、存储方式、模型维护、上线和可观测性都成为系统设计的一部分。
- 节目认为，这本书提供了一条构建 AI 系统的完整路线，虽然具体工具会随时间变化，但其中关于数据、模型和工程流程的视角仍有参考价值。

### 01:44:31-02:00:06：《编舟记》

- 《编舟记》讲述一群编辑花费约 15 年编写词典的故事，通过立项、采词、释义、校对、造纸和出版，呈现一项看似枯燥却要求极高准确性的工作。
- 词典收录的词语会不断变化，因此词典没有真正完成的时刻。编辑需要持续记录新词和新用法，还要处理定义中的循环引用、时代变化和表达是否公平等问题。
- 小说和电影都通过词义定义来表现人物关系与时代观念，例如“右”“东方”和“恋爱”的定义。词典工作因此不只是校对文字，也是在整理语言、历史和社会经验。
- 书中关于词典用纸的情节，把编辑对纸张触感的要求与造纸者的工艺结合起来，表现了严谨、协作和职业热爱。节目推荐先读原著，也认为电影能补充人物的神态和情感。

### 02:00:06-02:12:55：《诡计集成》与推理小说的边界

- 江户川乱步的《诡计集成》是一部关于推理小说诡计的评论和整理，书中回顾了犯罪者、现场痕迹、密室、时间、不在场证明、凶器以及隐藏人物和物品等类型。
- 节目提到约翰·迪克森·卡尔关于密室诡计的分类，说明密室写作可以被系统梳理，但分类本身并不能替代作品的叙事和人物塑造。
- 乱步不仅整理本格推理的类型，也讨论更奇特、甚至接近非自然设定的构思，并通过附录统计大量推理小说中的诡计类别，把它当作创作素材和边界索引。
- 好的推理小说不只是设计一个精巧诡计，还要通过人物、铺陈和伏笔让诡计合理并服务于整体叙事。节目以《白夜行》等作品说明，浅显的诡计也可以因人物和叙事而获得更强的作品张力。

## 核心观点

1. 技术选型应服从迁移成本、语言特征和维护目标；流行语言或社区声量不能替代具体工程判断。
2. AI 编程的可靠性取决于人的理解、提问和验收能力。成熟流程中的局部实现和胶水代码适合自动化，复杂架构和探索性问题仍需要人主导。
3. 开源贡献不只等于提交大量代码。高质量 Issue、问题复现、回答用户、连接社区、文档和课程协作，都能让开放生态持续运转。
4. AI 系统工程的关注点正在从单纯的代码扩展到数据、模型、部署、评估、观测和持续学习，工程方法也需要随之调整。
